# Worker runs in Docker on a sized-up-front plan with manual deploys; connect/disconnect reach it via a polled desired-state table; status gains a `reconnecting` state

The worker needs Docker, not Render's native Python runtime used by the web service. KGI's `libCGCrypt.so` signing library requires a system-level install — `chmod 755` plus a copy into `/lib/x86_64-linux-gnu/` (Ubuntu) or `/lib64/` (CentOS/RedHat) — and KGI's own cert-generation program (`KGI_CGCrypt genDat`) run against it, per KGI's own SuperPy docs. That level of filesystem control needs explicit `RUN` steps baked into a `Dockerfile` image; it isn't reliable in a native buildpack runtime's build/run split.

The worker starts on Render's `standard` plan rather than `starter`, sized up front rather than discovered empirically the way the web service's starter-plan tightness was. Holding several live broker connections open continuously plus a mirrored option-data copy has a worse failure mode under memory pressure than the web app's slow-page-load equivalent — a live-session crash drops real trading coverage, not just one request. Metrics/logging are added alongside so the plan can be right-sized against actual measured usage later. Deploys are manual only, not auto-deploy-on-push like the web service: a worker restart drops every live broker connection and forces a full relogin/resubscribe across the shared Watchlist, and — combined with the alert-timing decision below — would trigger a false-alarm disconnect page if it happened mid-session. Deploys are triggered deliberately from the Render dashboard, timed for the worker's own `stopped` window (`docs/adr/0009`). Liveness monitoring is layered: Render's own platform-level crash detection/restart is the first line (no new code, reuses what the platform already guarantees); an explicit heartbeat timestamp the worker writes on every scheduler tick, checked for staleness during market hours, is the second line, catching a hang that a crash restart wouldn't.

`/broker/connect` and `/broker/disconnect` (`docs/adr` for Phase 4, issue #24) reach the worker through a Supabase table the worker polls on its own scheduler cadence — no Redis, consistent with the ticks-stay-in-worker-memory decision (`docs/adr/0003`) and the polling precedent already set for the reverse, worker-to-browser direction (`docs/adr/0006`). It holds one row per (`user_id`, `broker`) recording the latest **desired state**, not a consumed command queue: the web route upserts desired state, the worker reconciles current vs. desired on each poll. This also settles what those two routes are actually for — `/broker/connect` is a narrow retry-after-failure action (the worker already auto-logs-in on schedule and auto-reconnects with backoff on its own; manual connect is for when that's exhausted) that doubles as "undo my own manual disconnect," and `/broker/disconnect` is a genuine manual stop usable any time, independent of failure state, writing the same `stopped` desired state as a scheduled end-of-day close.

That last point requires `worker_status` (`docs/adr/0004`) to grow a fourth state. Reconnect-with-backoff is capped, not infinite — after enough failed attempts the worker stops retrying rather than looping forever against a broker that may be rejecting auth. This makes "still retrying" and "gave up" genuinely different situations, so `worker_status` now has four states instead of two: `connected`; `stopped` (expected non-connection — scheduled close *or* a user's manual disconnect, no alert either way); `reconnecting` (actively retrying within the backoff window); `disconnected` (terminal — backoff exhausted, waiting for manual connect or tomorrow's scheduled login, alerts). The alert fires at the existing 15-30s persistence threshold from `docs/adr/0004` while still `reconnecting` — unchanged trigger point, not held back until exhaustion — and there is no second alert on the `reconnecting` → `disconnected` transition, avoiding a double-page for the same incident.
