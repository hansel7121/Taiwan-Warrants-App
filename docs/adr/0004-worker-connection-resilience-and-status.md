# Worker connection resilience: capacity-tier pooling, auto-reconnect, and status as shared state

Because the intended Watchlist is large, the worker's Connection Pool spreads subscribed codes across multiple broker connections per the account's Capacity Tier — KGI's tier is manually configured (starting at base: 30 symbols/connection, 2 connections), Fubon's is fixed (200 symbols/connection, 5 connections) with no tier concept. On disconnect, the worker auto-reconnects with backoff and resubscribes from the persisted Watchlist.

There is no live rebalancing across brokers: while one Broker Account is down, the codes it covered simply go dark — no Ticks, no Arb Signals for them — until that account reconnects, rather than the Connection Pool migrating them into the other broker's spare capacity mid-day. Outages are expected to be transient and are already alerted on, so mid-day migration would buy a few minutes of coverage in exchange for a redistribution path that has to be correct under partial failure.

Connection/health state is written to a `worker_status` table rather than embedded only in a one-off alert call, so the web UI's status indicator and the on-disconnect notifications are both just consumers of that same state — and a future monitoring agent (e.g. Hermes) can read the same table instead of requiring its own bespoke integration. Two notification channels fire on disconnect, independently: a Slack Incoming Webhook (`SLACK_WEBHOOK_URL`) and an ntfy.sh push (topic URL in an env var) — redundant on purpose, since a dropped connection during trading hours is exactly the kind of event where a single channel being unavailable (Slack down, phone not receiving push) shouldn't mean no alert at all.

A scheduled shutdown is not a failure and is recorded as a distinct state. When the worker closes its connections at the end of the trading day per `docs/adr/0009`'s market-hours gating, it writes `worker_status` = `stopped` for each Broker Account; only an unexpected mid-session drop writes `disconnected`. Both notification channels and the "Live scanning is offline" banner (per issue #25) fire on `disconnected` only, never on `stopped`, so routine nightly and weekend closures neither page anyone nor show a false-alarm banner.

Those notifications are throttled by a minimum-downtime threshold rather than firing on every blip: a disconnect has to persist past roughly 15-30 seconds — comfortably longer than a normal reconnect cycle — before either channel is triggered. Alerting on transient reconnects would produce exactly the alert fatigue that makes a second redundant channel worthless, since the failure mode is a person ignoring both.
