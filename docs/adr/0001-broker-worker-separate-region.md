# Broker worker runs as a separate Singapore-region service; web app and database stay put

The live broker-tick arb-detection loop (worker ↔ KGI/Fubon market-data connection) is the only latency-sensitive hop in the system; the existing web service's request patterns (manual page loads, a 15-minute refresh grid) and its Supabase reads/writes are not latency-sensitive at their current region. We considered migrating the whole stack (web service + database) to Singapore alongside the worker, but rejected it: that would force a full production cutover (DNS, a decommission window, re-testing every existing tab) for zero latency benefit on the parts that don't need it, and would couple migration risk to unrelated new-feature risk. Instead, only a new, additive Singapore-region Render Background Worker is introduced; it talks to the existing Supabase project from that region for its (infrequent) reads and writes.

One worker carries both brokers: `fubon_neo` and `kgisuperpy` are both Linux-native Python SDKs (KGI's needs its `libCGCrypt.so` signing library installed at build time), so no separate host is required for either.
